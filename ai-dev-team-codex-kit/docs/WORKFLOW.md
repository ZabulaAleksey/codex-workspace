# Рабочий процесс команды

## A. Маленький bugfix

1. Manager воспроизводит проблему или вызывает `explorer`.
2. Один write-agent делает минимальный fix.
3. `test_engineer` проверяет regression, если тестирование не тривиально.
4. `reviewer` нужен только для рискованных/межмодульных изменений.

## B. Фича в одном слое

1. `planner` или профильный специалист формулирует acceptance criteria.
2. Один write-agent реализует.
3. Тесты.
4. Обновить `docs/AI_STATUS.md`, если это roadmap-задача.

## C. Межсервисная фича

1. `architect` + встроенный `explorer` параллельно.
2. Manager фиксирует контракт между слоями.
3. Профильные write-agents работают только по непересекающимся областям.
4. Интеграционные тесты.
5. `reviewer`; при auth/network/secret изменениях ещё `security_reviewer`.
6. При performance-critical изменениях `performance_engineer`.
7. Обновить архитектуру/status/decision log.

## D. Следующий этап roadmap

Использовать `$implement-stage`.

## E. Исследование новой технологии

Использовать `docs_researcher`; сначала официальные docs / Context7, затем небольшой spike. Не добавлять dependency в production до фиксации причины и критериев успеха.

## F. Остановка циклов

Reviewer может вернуть замечания. Максимум два автоматических цикла "fix → review" за одну задачу. После двух неудачных циклов Manager должен сформулировать точный блокер вместо бесконечного агентного пинг-понга.
