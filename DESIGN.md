# Calm Blue UI — переносимый дизайн-контракт

> Статус: самостоятельный переносимый baseline (`v1.0`).
>
> Основание: desktop-референс светлого интерфейса с боковой навигацией и карточками объектов, 1800 × 822 px.
>
> Область применения: web-приложения, кабинеты, каталоги, dashboards, CRM, SaaS, порталы и сервисные продукты.

## 1. Назначение

Этот документ описывает самостоятельный визуальный язык, который можно перенести в новый или существующий проект без привязки к бренду, предметной области, языку, фреймворку или библиотеке компонентов.

Дизайн лучше всего подходит продуктам, которым нужны спокойный характер, ясная иерархия, светлые поверхности и заметное основное действие. Для игр, иммерсивных промосайтов, luxury-брендов, медиа с экспериментальной типографикой и сверхплотных профессиональных терминалов потребуется отдельная визуальная адаптация. При этом токены, доступность и правила совместимости можно сохранить.

Исходный экран каталога является примером композиции, а не обязательной структурой каждого проекта.

## 2. Как читать требования

В документе используются три уровня нормативности:

- **Core** — обязательное ядро: визуальные принципы, семантические цвета, интервалы, состояния и доступность.
- **Pattern** — рекомендуемый переиспользуемый компонент или способ компоновки.
- **Recipe** — необязательная композиция для конкретного типа экрана.

Проект может не использовать отдельный `Pattern` или `Recipe`, если он ему не нужен. Нельзя выборочно нарушать `Core`, не зафиксировав осознанное проектное переопределение.

## 3. Контракт интеграции без конфликтов

### 3.1. Приоритет источников

При внедрении в существующий проект действует следующий порядок:

1. прямые требования текущего проекта и пользователя;
2. локальный `DESIGN.md` и существующий бренд-контракт проекта;
3. существующие доступные компоненты и семантические токены;
4. этот переносимый baseline;
5. пример экрана из исходного референса.

Если в проекте уже есть эквивалентный токен или компонент, нужно сопоставить его с этим документом, а не создавать дубликат.

### 3.2. Namespace

Логические токены этой системы имеют префикс `cbui` (`Calm Blue UI`). В CSS их следует объявлять только внутри контейнера темы:

```css
[data-design-system="cbui"] {
  --cbui-color-accent: #4767f5;
  --cbui-color-text: #090909;
  --cbui-color-surface: #ffffff;
  --cbui-radius-control: 14px;
}
```

Правила совместимости:

- не объявлять токены `cbui` глобально в `:root`, если в приложении уже есть собственная тема;
- не использовать глобальные селекторы элементов вроде `button`, `input`, `a` и `h1` для стилизации системы;
- не добавлять глобальный CSS reset вместе с дизайном;
- компоненты ограничивать контейнером `[data-design-system="cbui"]`, CSS Modules, Shadow DOM или иным локальным механизмом проекта;
- при наличии проектной дизайн-системы сопоставить `cbui` с её семантическими токенами и не копировать значения повторно;
- не переопределять сторонние компоненты по внутренним class names;
- имена экспортируемых компонентов при необходимости также делать уникальными: `CbuiButton`, `CbuiCard`, `CbuiSidebar`;
- бренд, логотип, тексты, изображения и доменные статусы всегда принадлежат целевому проекту, а не этому baseline.

### 3.3. Карта адаптации

Перед внедрением заполнить короткую карту:

| Вопрос | Решение проекта |
|---|---|
| Контейнер темы | Например, `[data-design-system="cbui"]` |
| Основной accent | Оставить `#4767F5` или сопоставить с brand color |
| Шрифт | Inter, системный или существующий шрифт проекта |
| Радиусы | Сохранить baseline или сопоставить с существующей шкалой |
| Иконки | Выбрать один уже используемый набор |
| Layout | Sidebar, top navigation или другой shell |
| Локаль | Определяется проектом |
| Dark mode | Отдельная тема; значения в этом документе описывают light mode |

Такой адаптер является единственным местом, где переносимая система соприкасается с существующим визуальным контрактом проекта.

## 4. Визуальные принципы — Core

Интерфейс должен ощущаться:

- спокойным, доброжелательным и надёжным;
- современным, но не демонстративно технологичным;
- светлым и просторным;
- понятным без предварительного обучения;
- сфокусированным на одном главном действии в текущем контексте.

Практические правила:

- иерархия строится размером, весом, интервалами и только затем цветом;
- на одной поверхности используется не более одного визуально доминирующего действия;
- белые поверхности отделяются тонкой границей, а не тяжёлой тенью;
- связанные элементы стоят ближе друг к другу, чем соседние смысловые группы;
- декоративная графика не конкурирует с содержимым;
- интерфейс не уплотняется только ради размещения большего количества данных;
- доменная семантика не зашивается в универсальный компонент.

## 6. Цветовая система — Core

Система использует семантические роли. Названия конкретных цветов вроде `blue-500` не должны попадать в API компонентов.

| Token | Light value | Назначение |
|---|---:|---|
| `cbui.color.accent` | `#4767F5` | Главное действие, активная навигация, ссылки |
| `cbui.color.accent.hover` | `#3858E8` | Hover основного действия |
| `cbui.color.accent.pressed` | `#2F4BCB` | Pressed / active |
| `cbui.color.accent.soft` | `#F4F6FF` | Выбранные строки, мягкие badges |
| `cbui.color.text` | `#090909` | Основной текст |
| `cbui.color.text.muted` | `#626262` | Вторичные подписи |
| `cbui.color.text.disabled` | `#929292` | Недоступный текст |
| `cbui.color.surface` | `#FFFFFF` | Карточки, sidebar, controls |
| `cbui.color.surface.page` | `#FAFAFA` | Фон страницы |
| `cbui.color.surface.subtle` | `#F6F7F9` | Нейтральные badges и вложенные зоны |
| `cbui.color.border` | `#E4E4E4` | Обычные границы и разделители |
| `cbui.color.border.strong` | `#C9CDD5` | Hover или усиленная граница |
| `cbui.color.success` | `#13B97A` | Успешный статус |
| `cbui.color.warning` | `#F59E2F` | Внимание или срочность |
| `cbui.color.danger` | `#D64545` | Ошибка или разрушительное действие |
| `cbui.color.info` | `#4767F5` | Информационное состояние |
| `cbui.color.overlay` | `rgba(9, 9, 9, 0.48)` | Подложка modal / drawer |
| `cbui.color.focus` | `rgba(71, 103, 245, 0.32)` | Внешнее focus-ring |

Цвета `danger` и `overlay` добавлены как системные, хотя их нет на исходном экране. Они нужны, чтобы baseline был пригоден для полного интерфейса.

Правила:

- цвет не является единственным носителем смысла;
- статус сопровождается текстом, иконкой или доступным названием;
- белый текст на accent разрешён только после проверки контраста;
- brand color целевого проекта может заменить accent, если состояния hover, pressed и focus пересчитаны вместе с ним;
- dark mode не получается инверсией цветов: для него создаётся отдельная семантическая таблица.

## 7. Типографика — Core

Baseline не зависит от конкретного лицензируемого шрифта:

```css
font-family: Inter, ui-sans-serif, system-ui, -apple-system, "Segoe UI", sans-serif;
```

Если проект уже использует читаемый sans-serif, он имеет приоритет. Wordmark и декоративный display-font не заменяют интерфейсный шрифт.

| Token | Размер / line-height | Вес | Применение |
|---|---:|---:|---|
| `cbui.type.display` | `40 / 48 px` | `700` | Редкий крупный заголовок |
| `cbui.type.h1` | `32 / 40 px` | `700` | Заголовок страницы |
| `cbui.type.h2` | `24 / 31 px` | `700` | Заголовок секции или карточки |
| `cbui.type.h3` | `20 / 27 px` | `600` | Подсекция |
| `cbui.type.body-lg` | `18 / 26 px` | `400` | Выделенный основной текст |
| `cbui.type.body` | `16 / 24 px` | `400` | Базовый текст и controls |
| `cbui.type.body-sm` | `14 / 20 px` | `400` | Вторичная информация |
| `cbui.type.caption` | `12 / 16 px` | `500` | Короткие подписи |
| `cbui.type.action` | `16 / 20 px` | `600` | Кнопки и активная навигация |

Правила:

- основной текст выравнивается по левому краю;
- обычный регистр предпочтительнее капса;
- строки основного текста ограничиваются примерно `45–75` символами;
- масштабирование текста до `200%` не должно скрывать функции;
- длинные пользовательские значения нельзя обрезать без пути к полной версии.

## 8. Интервалы, размеры и геометрия — Core

### 8.1. Шкала интервалов

```text
cbui.space.0 = 0
cbui.space.1 = 4 px
cbui.space.2 = 8 px
cbui.space.3 = 12 px
cbui.space.4 = 16 px
cbui.space.5 = 20 px
cbui.space.6 = 24 px
cbui.space.7 = 32 px
cbui.space.8 = 40 px
cbui.space.9 = 48 px
cbui.space.10 = 64 px
```

Если наблюдаемый размер близок к шкале, используется ближайший token. Например, визуальный отступ `30 px` реализуется как `32 px`, если pixel-perfect совпадение не является отдельным требованием.

### 8.2. Радиусы и границы

```text
cbui.radius.small   = 8 px
cbui.radius.control = 14 px
cbui.radius.card    = 20 px
cbui.radius.round   = 999 px

cbui.border.default = 1 px solid cbui.color.border
cbui.border.focus   = 3 px solid cbui.color.focus
```

- `round` используется только для avatar, status dot и действительно капсульных badges;
- карточки и controls не смешивают случайные радиусы;
- изменение толщины границы в hover не должно менять геометрию элемента.

### 8.3. Elevation

```text
cbui.shadow.none     = none
cbui.shadow.floating = 0 10px 30px rgba(9, 9, 9, 0.10)
cbui.shadow.overlay  = 0 20px 60px rgba(9, 9, 9, 0.16)
```

Обычная карточка использует границу без тени. Тени предназначены для dropdown, popover, modal и других элементов над основным слоем.

### 8.4. Размеры взаимодействия

- минимальная область нажатия: `44 × 44 px`;
- обычная высота control: `48 px`;
- крупное основное действие: `56 px`;
- обычная icon button: `48 × 48 px`;
- крупная icon button рядом с CTA: `56 × 56 px`;
- минимальный промежуток между независимыми touch-targets: `8 px`.

## 9. Motion — Core

```text
cbui.motion.fast   = 120 ms
cbui.motion.normal = 180 ms
cbui.motion.slow   = 240 ms
cbui.motion.ease   = cubic-bezier(0.2, 0, 0, 1)
```

- motion объясняет смену состояния, а не украшает интерфейс;
- hover и press не перемещают layout;
- skeleton не должен агрессивно мерцать;
- `prefers-reduced-motion: reduce` отключает необязательные перемещения и сокращает переходы;
- autoplay со звуком запрещён.

## 10. Базовые компоненты — Patterns

### 10.1. Buttons

Обязательные варианты:

- `primary` — залитый accent, одно главное действие в локальном контексте;
- `secondary` — белая поверхность и accent-border;
- `tertiary` — текстовое действие без отдельной поверхности;
- `danger` — только для подтверждённо разрушительных действий;
- `icon` — всегда имеет доступное текстовое название.

Все варианты поддерживают `default`, `hover`, `focus-visible`, `pressed`, `disabled` и `loading`. Во время loading ширина кнопки не меняется. Иконка перед текстом имеет размер `20–24 px`.

### 10.2. Form controls

Input, textarea, select, checkbox, radio и switch используют единый набор состояний:

- label расположен снаружи и не заменяется placeholder;
- helper text и error message занимают предсказуемое место;
- обычная высота input/select — `48 px`;
- фон — `surface`, граница — `border`, radius — `control`;
- focus показывает accent-border и внешнее focus-ring;
- error показывает danger-border и текстовую причину;
- disabled визуально отличается и имеет корректный нативный атрибут;
- валидация не зависит только от цвета.

### 10.3. Cards

Универсальная карточка:

- белая поверхность;
- граница `1 px`;
- radius `20 px`;
- внутренний отступ `24–32 px` на desktop и `16–20 px` на compact-экранах;
- без тени в основном потоке;
- header, content и actions используются только при наличии соответствующих данных.

Карточка не считается ссылкой автоматически. Если кликабельна вся поверхность, вложенные действия должны оставаться корректными для клавиатуры и assistive technologies.

### 10.4. Navigation

- пункт содержит иконку и текст либо только текст;
- активное состояние использует `accent.soft` и accent-текст;
- hover слабее активного состояния;
- группировка отмечается интервалом, заголовком или разделителем;
- иконка без текста допустима только при устойчиво понятном значении и наличии tooltip / accessible name;
- активность определяется не только цветом, но также фоном, маркером или весом текста.

### 10.5. Badges и statuses

- badge короткий и не содержит основное действие;
- нейтральный badge использует `surface.subtle`;
- смысловой badge использует мягкий фон и текст достаточного контраста;
- status dot обязательно дублируется доступным текстом;
- значения статусов определяет проект: универсальный зелёный индикатор не означает «онлайн» сам по себе.

### 10.6. Data display

- метрики объединяются в компактные смысловые группы;
- таблица используется для сравнения однотипных структурированных данных;
- карточки используются, когда у объектов есть изображение, описание и несколько действий;
- на узком экране таблица либо прокручивается с явным affordance, либо превращается в строки-карточки без потери labels;
- pagination, sorting и filters сохраняют состояние предсказуемо.

### 10.7. Feedback и overlays

Самодостаточная реализация должна предусматривать:

- inline error рядом с источником проблемы;
- alert для сообщения уровня секции;
- toast для краткого результата завершённого действия;
- skeleton для первичной загрузки структуры;
- progress indicator для длительного действия;
- empty state с объяснением и одним следующим шагом;
- modal для короткого блокирующего решения;
- drawer для вспомогательного контекста;
- tooltip только для краткого пояснения, не для критичной информации.

Modal и drawer удерживают keyboard focus, закрываются предсказуемо и возвращают focus инициатору.

### 10.8. Media и иконки

- изображения используют заранее заданное соотношение сторон и `object-fit: cover`;
- avatar обычно круглый, крупное preview — со скруглением `control`;
- meaningful image получает содержательный `alt`, декоративное — пустой `alt`;
- иконки выбираются из одного outline-набора с округлыми окончаниями;
- базовый размер иконки: `20–24 px`, в навигации допустим `24–28 px`;
- нельзя смешивать outline, filled и duotone внутри одной функциональной группы;
- логотип и wordmark всегда заменяются активами целевого проекта.

## 11. Application shell — Recipe

Исходный визуальный характер лучше всего передаёт двухчастный shell:

- sidebar на desktop: ориентировочно `272–280 px`;
- рабочая область: `surface.page`;
- основной контент: `max-width: 960 px` для ленты и `1200–1280 px` для dashboard/grid;
- горизонтальный page gutter: `clamp(16px, 4vw, 48px)`;
- вертикальный интервал между крупными секциями: `20–32 px`;
- sidebar использует белую поверхность без тяжёлой тени.

```text
┌────────────────────┬───────────────────────────────────────────────┐
│ Brand              │ Page header                                   │
│                    │                                               │
│ Primary navigation │ Main content                                  │
│                    │ ┌───────────────────────────────────────────┐ │
│ Secondary group    │ │ Section / card / data view                │ │
│                    │ └───────────────────────────────────────────┘ │
│ Account / support  │                                               │
└────────────────────┴───────────────────────────────────────────────┘
```

Sidebar является рецептом, а не обязательным элементом стиля. Для сайта с малым числом разделов можно использовать top navigation, сохранив токены и визуальные принципы.

Декоративный outline-паттерн на фоне допустим, если он тематически подходит проекту. Его opacity должен быть настолько низким, чтобы он исчезал из внимания раньше основного контента. Без подходящей графики используется чистый `surface.page`.

## 12. Каталог объектов — Recipe из референса

Этот recipe подходит специалистам, товарам, курсам, объявлениям, кандидатам, помещениям и другим сравнимым сущностям.

### 12.1. Desktop-карточка

- одна колонка карточек с интервалом около `20 px`;
- медиа слева, информация справа;
- квадратное preview около `256–272 px`;
- gap между preview и содержимым: `24 px`;
- последовательность: title, optional badge, metadata, metrics, description, contextual action;
- описание ограничивается по высоте, но полная версия доступна на detail page;
- действия выровнены в одну строку: contextual value, secondary action, primary action;
- высота карточки определяется содержимым и не фиксируется жёстко.

### 12.2. Независимость от домена

Следующие элементы исходного экрана являются только примерами и не входят в Core:

| Референс | Универсальная роль |
|---|---|
| Имя специалиста | `entity.title` |
| Опыт и специализация | `entity.metadata` |
| Цена, отзывы, сессии | `entity.metrics[]` |
| Ближайшее время | `entity.contextualValue` |
| Чат | `entity.secondaryAction` |
| Просмотр доступности | `entity.primaryAction` |
| Бейдж квалификации | `entity.badge` |
| Зелёная точка | `entity.status` с проектной семантикой |

Компонент не должен содержать слова, валюту, формат дат, иконки или business rules конкретной предметной области.

## 13. Другие композиции — Recipes

### 13.1. Detail page

- page header с title и основным действием;
- summary-card для ключевых атрибутов;
- основной текст в колонке комфортной длины;
- secondary data в отдельных секциях или sidebar;
- действия не дублируются без необходимости.

### 13.2. Form flow

- одна логическая группа на секцию;
- labels всегда видимы;
- primary action после полей, secondary action визуально слабее;
- ошибки показываются у поля и кратко суммируются сверху при длинной форме;
- при многошаговом процессе показывается текущий этап и возможность вернуться.

### 13.3. Dashboard

- summary metrics располагаются в одинаковых карточках;
- главный insight визуально сильнее вторичных метрик;
- графики получают title, legend и текстовое представление значений;
- цветовые серии остаются различимыми без зависимости только от оттенка;
- плотность может быть выше каталога, но использует ту же шкалу интервалов.

## 14. Адаптивность — Core

Breakpoints являются стартовыми ориентирами и могут быть сопоставлены с существующей системой проекта:

```text
compact: < 640 px
medium:  640–959 px
wide:    960–1279 px
x-wide:  >= 1280 px
```

Принципы важнее названий устройств:

- layout перестраивается, когда содержимое перестаёт помещаться, а не по названию устройства;
- sidebar на medium может сворачиваться, а на compact заменяется menu/drawer или bottom navigation;
- многоколоночная карточка превращается в одну колонку;
- primary action на compact обычно занимает доступную ширину;
- группы метрик переносятся целиком;
- текст и действия не перекрываются при zoom до `200%`;
- горизонтальная прокрутка всей страницы не допускается при ширине viewport от `320 px`;
- декоративный паттерн можно скрывать на compact.

Container queries предпочтительны для переиспользуемых карточек, если стек проекта их поддерживает.

## 15. Состояния страниц — Core

Каждый экран с асинхронными данными проектируется минимум в состояниях:

- `loading` — структура узнаваема, действия не скачут после загрузки;
- `content` — обычное рабочее состояние;
- `empty-first-use` — объясняется назначение и предлагается первый шаг;
- `empty-filtered` — предлагается изменить или сбросить фильтры;
- `partial` — доступные данные остаются полезными при частичной ошибке;
- `error-recoverable` — видна причина понятного уровня и повтор действия;
- `offline`, если проект зависит от постоянной сети;
- `permission-denied`, если есть роли и доступы.

Скрывать всю страницу из-за ошибки одного вторичного блока не следует.

## 16. Контент и локализация — Core

- язык, валюта, часовой пояс, формат даты и plural rules задаются проектом;
- UI-copy хранится отдельно от компонентов;
- компоненты выдерживают расширение текста примерно до `30–40%`;
- даты и деньги форматируются средствами локали, а не конкатенацией строк;
- числа и единицы измерения не теряют связь при переносе;
- направление `RTL` учитывается через logical CSS properties, если оно входит в аудиторию проекта;
- тон текста — ясный, человечный и прямой;
- подписи действий называют результат: «Сохранить изменения», а не «ОК».

Украинские тексты, гривны и названия из исходного изображения не являются требованиями этого baseline.

## 17. Доступность — Core

- целевой уровень — WCAG 2.2 AA;
- интерфейс полностью доступен с клавиатуры;
- порядок focus соответствует визуальному порядку;
- `focus-visible` заметен на всех поверхностях;
- минимальная область нажатия — `44 × 44 px`;
- семантические HTML-элементы предпочтительнее имитации через `div`;
- у icon-only controls есть accessible name;
- изображения, charts и статусы имеют текстовый эквивалент;
- форма связывает label, helper и error через корректные атрибуты;
- ошибки не сообщаются только цветом;
- видео не запускается автоматически со звуком и предоставляет captions, если содержит речь;
- содержимое остаётся рабочим при zoom `200%` и reflow на ширине `320 CSS px`;
- contrast проверяется после любого изменения accent или статусов.

## 18. Технологическая независимость

Дизайн не требует React, Vue, Svelte, Tailwind, shadcn/ui или конкретной icon library. При переносе:

- семантика компонентов сохраняется независимо от фреймворка;
- существующий проектный primitive переиспользуется, если удовлетворяет контракту;
- CSS-in-JS, utility classes и обычный CSS считаются равноправными способами реализации;
- системные tokens хранятся в одном каноническом месте;
- magic numbers допустимы только для уникальной композиции, а не вместо системных токенов;
- сторонняя библиотека адаптируется через публичный theme API, без хрупких внутренних селекторов.

## 20. Критерии соответствия стилю

Интерфейс согласован с Calm Blue UI, если:

- использует светлые поверхности, спокойный accent и ясную типографическую иерархию;
- группирует контент воздухом и тонкими границами;
- не злоупотребляет тенями, цветами и декоративными эффектами;
- использует согласованные радиусы, интервалы и размеры controls;
- явно различает primary, secondary и passive information;
- имеет состояния loading, empty, error и disabled;
- адаптируется без потери функций и поддерживает WCAG 2.2 AA;
- подключён через namespace или token mapping без конфликта с проектом;
- не наследует бренд, язык и бизнес-правила исходного референса.

## 21. Известные границы baseline

Документ самодостаточен как дизайн-контракт и основа реализации, но не заменяет:

- уникальную бренд-айдентику и логотип;
- продуктовые требования и информационную архитектуру;
- исследование пользователей;
- точные макеты сложных или уникальных экранов;
- юридические требования конкретной отрасли;
- проверку реализации в браузере и на реальных устройствах;
- отдельную спецификацию dark mode, email, native mobile или print.

Эти части добавляются в локальный `DESIGN.md` выбранного проекта, не изменяя переносимое ядро без необходимости.
