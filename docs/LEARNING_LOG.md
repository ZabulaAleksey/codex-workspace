# Учебный журнал

## 2026-08-13 — Read-only проверка project overlay

### Задача

Превратить требования КАРКАСА в воспроизводимый допуск одного независимого repository и зафиксировать последовательную очередь rollout.

### Что изменили

Добавлен `tools/validate_project_overlay.py` с human/JSON output, unit-тесты для complete, incomplete, duplicate, non-Git и повторного запуска, а также единый `docs/PROJECT_CATALOG.md`. Workspace manifest теперь требует канонические SPEC, framework-документы и validator.

### Существенные команды

```powershell
py -3 -B -m unittest tools/test_validate_project_overlay.py -v
py -3 -B tools/validate_project_overlay.py projects/text-recognition-core
py -3 -B tools/validate_context.py
git diff --check
```

### Почему выбран такой подход

Validator отделяет диагностику от изменений: он не исправляет repository и не выполняет его код. Точные дубликаты сравниваются по SHA-256, а `git -c safe.directory=<target>` ограничивает доверие одним процессом без изменения глобального Git config.

### Как повторить самостоятельно

1. Запустить validator на эталонном complete repository.
2. Запустить его на incomplete repository и прочитать стабильные issue codes.
3. Повторить запуск и сравнить `git status` до и после.
4. При локальной automation создать осмысленный compatibility audit, не копируя глобальные возможности.
5. Обновить Markdown-каталог после подтверждённого результата rollout.

### Результат пилота

`off-screen-canvas` получил только SPEC, framework-документы и тонкую маршрутизацию в `AGENTS.md`. Runtime-файлы не менялись. Validator и SessionStart forward-test прошли; следующий отдельный кандидат зафиксирован как `electro-tutor`.

## 2026-08-11 — Интеграция SDD в AI Dev Team

### Задача

Добавить разработку на основе спецификаций и выборочную маршрутизацию инженерных правил.

### Что исследовали

Сопоставили существующие глобальные инструкции, skills, hooks и project presets с требованиями SDD из предоставленного публичного чата.

### Основные команды

`git status -sb` — проверка ветки и незавершённых изменений.

`rg` — поиск существующих правил, ссылок и точек интеграции.

`git diff --check` — проверка пробелов и корректности патча.

### Как была устроена проблема

Требования, архитектура, план и prompt могли смешиваться. Отсутствовали отдельный канонический слой SPEC и выборочные правила по этапу SDLC, домену и стеку.

### Что изменили

Добавлены SDD, SDLC, mode, domain и stack rules; глобальные инструкции, skills и hook подключены к новой маршрутизации.

### Почему выбран такой подход

Подробные правила хранятся раздельно и загружаются только по необходимости. Это сохраняет контекст и не создаёт отдельную AI-команду для каждого этапа.

### Что пошло не так

Встроенный браузер не подключился из-за сбоя среды Windows. Публичный чат был прочитан напрямую как UTF-8 и использован только как источник требований.

Runtime-тест установщика обнаружил, что `TrimStart('\\','/')` передавал двухсимвольную строку вместо `char`. Аргументы заменены на явные символы, после чего тест повторён.

### Проверки

Проверены Markdown, пути, YAML frontmatter, TOML/JSON/Python, манифест и `git diff --check`. Runtime-тест подтвердил копирование SPEC установщиком и загрузку SDD-контекста hook-скриптом.

Официальный `quick_validate.py` не запустился из-за отсутствия PyYAML в системном Python. Эквивалентная локальная проверка обязательных полей, имён и структуры frontmatter прошла для всех skills.

### Как повторить вручную

1. Определить сложность, режим, этап SDLC, домен и стек.
2. Найти соответствующую SPEC через `specs/README.md`.
3. Загрузить только необходимые правила.
4. Реализовать требования и связать их с тестами.
5. Проверить соответствие SPEC перед завершением.

### Что стоит изучить

Spec-Driven Development, traceability требований, acceptance criteria и progressive disclosure контекста.

## 2026-08-11 — перенос рабочей области в домашний каталог

### Задача

Перенести AI Dev Team и рабочие проекты из старой директории в `~/codex-workspace`, сохранив отдельные Git-репозитории и исключив их из внешнего Git.

### Что исследовали

Проверены границы Git, активный глобальный `AGENTS.md`, trust-настройки Codex, текущий каталог preset-шаблонов и размеры переносимых репозиториев.

### Основные команды

`git rev-parse --show-toplevel`

Определяет корень каждого самостоятельного репозитория и помогает не смешивать изменения.

`git check-ignore -v projects/<project>`

Показывает правило `.gitignore`, из-за которого вложенный проект не попадает во внешний репозиторий.

`Get-FileHash -Algorithm SHA256`

Подтверждает целостность копии перед удалением исходного каталога.

### Как была устроена проблема

Каталог `projects/` внешнего репозитория содержал preset-шаблоны, а рабочие проекты находились отдельно от AI Dev-репозитория. Поэтому простое объединение создало бы смешение шаблонов и самостоятельных Git-репозиториев.

### Что изменили

Preset-шаблоны перенесены в `presets/`. Каталог `projects/` теперь предназначен только для независимых репозиториев и игнорируется внешним Git. AI Dev Team находится в `~/codex-workspace`, а глобальные инструкции — в `~/.codex/AGENTS.md`.

### Почему выбран такой подход

Разделение `presets/` и `projects/` сохраняет шаблоны в истории AI Dev Team, но не позволяет внешнему Git случайно захватить код, историю или секреты рабочих проектов.

### Что пошло не так

Стандартный редактор патчей перестал работать после удаления старого Git-root. Для текстовых изменений использован проверяемый `git apply`, а массовые изменения путей выполнены только в заранее перечисленных файлах.

### Проверки

Копия AI Dev Team совпала по 585 файлам. Копия `video-chronicle` совпала по 10 947 файлам и 563 063 258 байтам. В обоих случаях расхождений SHA-256 не обнаружено.

### Как повторить вручную

1. Найти все `.git` и проверить статус каждого репозитория.
2. Освободить имя `projects/` от шаблонов.
3. Настроить whitelist в корневом `.gitignore`.
4. Скопировать каталоги и сверить SHA-256.
5. Удалять источники только после нулевого числа расхождений.
6. Обновить trust-пути и перезапустить Codex.

### Что стоит изучить

Вложенные Git-репозитории, правила отрицания в `.gitignore`, discovery `AGENTS.md` и проверка целостности SHA-256.

## 2026-08-11 — согласование глобального и проектного контекста Codex

### Задача

Проверить связи между `~/.codex` и `~/codex-workspace`, устранить дублирование и подготовить воспроизводимые промпты для другого компьютера.

### Что исследовали

Проверены правила discovery `AGENTS.md`, активный и рекомендуемый `config.toml`, доверенные проекты, пользовательские агенты, skills, hooks, rules и MCP.

### Основные команды

`codex mcp list`

Показывает реально активные MCP, в отличие от шаблонов, которые только хранятся в репозитории.

`git diff --no-index ~/.codex/AGENTS.md global/codex/AGENTS.md`

Выявляет расхождение между установленным глобальным контекстом и его каноническим шаблоном.

### Как была устроена проблема

Корневой `AGENTS.md` превышал стандартный лимит 32 КиБ, глобальный шаблон дублировал правила вместо короткой маршрутизации, а агенты, hooks, rules и skills из набора ещё не были установлены.

### Что изменили

Подробные учебные правила вынесены в `docs/MENTORING_GUIDE.md`, глобальный шаблон синхронизирован с коротким мостом, а установщик перестал создавать идентичный дубликат. Одноразовый сценарий переноса позднее удалён после завершения миграции рабочей области.

### Почему выбран такой подход

Короткая автоматически загружаемая цепочка уменьшает постоянный расход контекста. Подробные правила остаются доступны по явным ссылкам и загружаются только для подходящих задач.

### Что пошло не так

После переноса за пределы прежнего sandbox-root стандартный редактор патчей не смог обновить файлы. Изменения применялись проверяемыми Git-патчами; детерминированное разбиение большого Markdown выполнено с проверкой точного числа строк.

### Проверки

Проверены размеры контекстной цепочки, TOML/JSON/Python, синтаксис PowerShell, локальные Markdown-ссылки, Git-границы и отсутствие секретов в diff.

### Как повторить вручную

1. Сравнить активный глобальный файл с шаблоном.
2. Посчитать общий размер загружаемых `AGENTS.md`.
3. Вынести подробные справочные правила из автоматического контекста.
4. Проверить реально установленные agents, hooks, rules и skills.
5. Проверить trust для каждого отдельного репозитория.
6. Перезапустить Codex и просмотреть `/hooks`, `/agent`, `/skills` и `/mcp`.

### Что стоит изучить

Каскад `AGENTS.md`, project-scoped config layers, trust-модель Codex и progressive disclosure контекста.

## 2026-08-13 — единое определение проектного КАРКАСА

### Задача

Сделать понятия «КАРКАС» и «АВТОМАТИЗАЦИЯ КОНТЕКСТА» одинаково применимыми ко всем проектам `codex-workspace`, не перенося OCR-специфику Text Recognition Core в общую инфраструктуру.

### Что изменили

Добавлен канонический `docs/PROJECT_FRAMEWORK.md`, короткая маршрутизация в workspace/global `AGENTS.md` и общий Skill `bootstrap-project-framework`. README, manifest и каталог проектов синхронизированы.

### Почему выбран такой подход

Полный исходный brief содержал полезные определения, но также старые имена status-файлов и TRC-примеры. Нейтральный канонический документ сохраняет смысл, следует текущей context policy и не расходует контекст каждого проекта на нерелевантную предметную область.

### Проверки

Выполнены `tools/validate_context.py`, Skill `quick_validate.py` в UTF-8-режиме, `git diff --check` и независимый read-only forward-test. Forward-test построил lean overlay, унаследовал общие возможности и остановился до product code.

### Как повторить вручную

1. Прочитать `docs/PROJECT_FRAMEWORK.md` и context policy.
2. В новом repository вызвать `$bootstrap-project-framework` или попросить «создай КАРКАС».
3. Проверить canonical SPEC, один AI_STATUS/AI_PLAN и compatibility matrix.
